# AGENTS.md: cs-survival-guide

Standing rules for any coding agent working in this repository. Read this before every task.

## What this project is

`cs-survival-guide` is the source of the [CS Survival Guide](https://jwallace145.github.io/cs-survival-guide/),
a Zensical site of hand-written pages on data structures, algorithms and other computer science
fundamentals. It is the companion to [cs-survival-kit](https://github.com/jwallace145/cs-survival-kit),
the PyPI library whose docstrings and benchmark results this site renders. The guide explains the
ideas; the kit is the code.

The owner (Jimmy) writes the pages: they are his learning record, in his voice. Everything else (the
`benchmark` macro, scripts, CI, release plumbing, site configuration) is the agent's job. When asked to
work on a page, draft and edit in the voice of the existing pages under `docs/`, check the maths, and
keep every claim about the library consistent with its docstrings.

## Hard boundaries

1. **Never merge a PR, push directly to `main`, or enable auto-merge.** Every change lands through a PR
   that Jimmy merges. This includes Release Please's release PRs and the automated `Bump Kit` PRs.
2. **Never edit `version.txt`, `CHANGELOG.md`, or the footer version in `zensical.toml` by hand.**
   Release Please owns them.
3. **Never edit `kit-version.txt` in a PR that does anything else.** The `Bump Kit` workflow opens an
   isolated `fix(deps): bump cs-survival-kit to X.Y.Z` PR; run it from the Actions tab with a `version`
   input to retry a missed release or pin back. A hand-written bump is acceptable only when the
   workflow cannot do it, and then it must be the only change in the PR, with that exact title.
4. **Never type a benchmark number into a page.** Numbers come only from the `benchmark` macro, so
   they always belong to the pinned library release. Prose describes the shape of a curve (flat,
   linear, quadratic, the ratio between two cases), never a measured value, because the values change
   with every release and GitHub runners are noisy.
5. **Never weaken the strict benchmark check.** CI sets `GUIDE_BENCHMARKS_STRICT=1` so a page that
   names a benchmark or case the pinned library lacks fails the build. Do not unset it, catch around
   it, or make the macro swallow the error; fix the name or wait for the release that has it.
6. **Never commit `lib/`, `site/`, `.cache/`, or `zensical.generated.toml`.** They are build inputs and
   outputs, generated by the scripts, and git-ignored.

## Conventions

- **Commits:** Conventional Commits, validated in CI on PR titles. PRs are squash-merged and **the PR
  title alone becomes the commit on `main`**; the description is discarded. Mark a breaking change with
  `!` in the title, not a `BREAKING CHANGE:` footer.
  - `feat(<area>): add <page> guide` → minor bump. `fix(<area>): ...` → patch. `docs`, `refactor`,
    `chore` → no release, shown in the changelog. `ci`, `build`, `test`, `style` → hidden.
  - Scopes are suggestions, not enforced: `data-structures`, `algorithms`, `math`, `system-design`,
    `distributed-systems`, `databases`, `networking`, `operating-systems`, `concurrency`, `ai`, `site`,
    `ci`, `deps`. Match the `docs/` directory of the page being changed.
  - After a `feat` or `fix` merges, check that Release Please opened or updated its release PR. If it
    did not, read the Release Please workflow log for a commit it could not parse.
- **Versioning:** SemVer in `0.x`, managed by Release Please. Breaking changes bump the minor version
  until `1.0.0`, which is a deliberate milestone (`Release-As: 1.0.0` footer), never automatic.
- **Tooling:** Python 3.13 in CI, a plain venv locally (`python3 -m venv .venv`), dependencies pinned in
  `requirements.txt` (`zensical`, `mkdocstrings-python`), tests with the standard-library `unittest`.
  Add a dependency only when a page or the macro genuinely needs it, and pin it.
- **Prose:** wrap markdown at about 78 columns like the existing pages. British spelling
  (behaviour, colour), with the conventional spelling of technical terms such as amortized.

## Page standard (for new guide pages)

Follow `docs/data-structures/doubly-linked-list.md`, the most recent page, exactly:

- Front matter `render_macros: true` if and only if the page calls a macro. Rendering is opt-in so
  braces on other pages are left alone.
- One `#` title, then an opening paragraph that says what the thing is in plain terms, names
  real-world examples where they exist, and links the guide's implementation with a mkdocstrings
  cross-reference such as ``[`DynamicArray`][cs_survival_kit.data_structures.dynamic_array.DynamicArray]``.
  Link the related pages (the structure it builds on, or the one it is usually compared against).
- A `## How it works` section next, with a Mermaid diagram when the structure has a shape worth
  drawing. Then one `##` section per idea, each built around what an operation costs and why.
- A comparison section (`## Linked list or dynamic array?`, `## Doubly or singly?`) when there is a
  natural rival.
- A `## Measured` section with one `###` subsection per benchmark, each explaining what the benchmark
  does and how to read the chart before the `{{ benchmark("...") }}` call, and what the shape shows
  after it.
- A closing `## Complexity` table (`Operation | Time | Notes`) that agrees with the `Complexity:` table
  in the library class's docstring. If they disagree, say so and ask which is right; do not silently
  pick one.
- Maths in LaTeX via `$...$` and `$$...$$` (pymdownx.arithmatex with MathJax). Derivations lean on
  `docs/math/cheat-sheet.md`; add a formula there, with its own anchor, rather than re-deriving it
  inline. Use `??? note` collapsible admonitions for optional detail.
- Link operations to their reference entries (``[`pop_back`][cs_survival_kit...DoublyLinkedList.pop_back]``)
  rather than describing where to find them.
- Add the page to `nav` in `zensical.toml`, in the matching section, in the order the pages read best.
  The Reference section is appended automatically and is never listed there.
- Every cross-reference must resolve against the library version pinned in `kit-version.txt`. A page
  that references a name or benchmark only in an unreleased library branch cannot merge until that
  release is pinned; say so in the PR description and keep the names identical on both sides.

## Benchmark macro standard

`{{ benchmark(name, view="both", cases=None, chart=True) }}` renders a log-log SVG line chart plus a
table from the results shipped inside the installed library.

- `name` is the first argument to `Benchmark(...)` in the library's `benchmarks/bench_*.py`, of the
  form `<module>.<operation>` or `<module>.<operation>.<variant>`. Case labels are the column names.
- `view="both"` shows total time and per-item time in tabs; `"total"` or `"per_item"` shows one.
  Per-item only exists for benchmarks created with `per_item=True`.
- A chart shows at most four cases. The four colours in `docs/stylesheets/benchmarks.css` were measured
  as a set to stay distinguishable, including for colour-blind readers, on both themes; there is no
  fifth. Pass `cases=[...]` to pick and order columns, or `chart=False` for tables only.
- Without the library under `lib/`, or when the pinned version is not on PyPI, the macro renders a
  warning box and the site still builds. That is the drafting mode; it is not acceptable on `main`.

## Tooling standard (for code the agent writes)

- `guide_macros.py` and `tests/test_guide_macros.py` are agent-owned. Every change to the macro gets a
  test; run `python -m unittest discover -s tests`. Tests build their own results documents and never
  depend on a real `lib/`.
- Scripts under `scripts/` are `bash` with `set -euo pipefail`, run from any directory
  (`cd "$(dirname "$0")/.."`), and explain their purpose in a header comment. They must keep working
  when the library is absent: a missing or unreleased kit is a warning, not a failure.
- Workflows under `.github/workflows/` start with a comment that says what they do and when they run.
  Pin actions to a major tag and note any that have no moving tag.
- Keep the build reproducible: the site must build identically from `scripts/zensical.sh build --clean`
  locally and in CI.

## Quality gates (all must pass in CI)

On every PR, `Build Docs` runs exactly what `Deploy Docs` runs on `main`:

```bash
pip install -r requirements.txt
scripts/install-kit.sh                   # pinned kit into lib/, or warn and skip
python -m unittest discover -s tests
GUIDE_BENCHMARKS_STRICT=1 scripts/zensical.sh build --clean
```

`Conventional Commits` validates the PR title. `PR Preview` publishes the built site to
`https://jwallace145.github.io/cs-survival-guide/pr-preview/pr-<number>/` and comments the link; use it
to check rendering, cross-references and charts before asking for review. Run the gate locally and
report its actual output before opening a PR.

## The library

- `kit-version.txt` is the single source of truth for which `cs-survival-kit` version the site
  documents. `scripts/install-kit.sh` installs it into `lib/` (no dependencies, sources only), and
  `scripts/zensical.sh` appends `zensical.reference.toml` to the config so mkdocstrings and api-autonav
  render the Reference section, titled with that version. No reference markdown is written by hand.
- Every class and function in the Reference section has a "View on GitHub" link to its lines in the
  library repository at the pinned release tag (`main` for a local checkout). The link comes from the
  template overrides under `templates/mkdocstrings/` and the `source_url` set in
  `zensical.reference.toml`; `scripts/zensical.sh` substitutes the git ref.
- The guide's version and the library's are independent. A library release reaches the site only
  through the `Bump Kit` PR, which is a `fix(deps)` and therefore a patch release of the guide.
- To preview unreleased docstrings or benchmark names from a local checkout:

  ```bash
  scripts/link-local-kit.sh ../cs-survival-kit   # symlink lib/cs_survival_kit at the checkout
  scripts/zensical.sh serve                      # Reference section titled "local"
  scripts/install-kit.sh                         # back to the pinned release
  ```

  The symlinked results file is the library's empty tracked copy, so charts render as warning boxes.
  To see real charts, run the benchmark in the library checkout
  (`uv run python -m cs_survival_kit.bench benchmarks/bench_<module>.py`), serve the guide, then
  `git checkout` the library's `src/cs_survival_kit/_data/benchmarks.json` so no numbers are committed
  there. Restart `scripts/zensical.sh serve` after switching between symlink and install, or after
  editing `zensical.toml`; the generated config is assembled once at startup.
- When a library change renames or removes a public name or a benchmark, grep `docs/` for the old
  dotted path or `benchmark("` name before the next bump; the break shows up here, one release later.
